# web

Next.js (App Router) frontend: TypeScript strict, Tailwind CSS, ESLint, Vitest + Testing Library for unit tests, Playwright for end-to-end tests.

## Develop

The app needs the local Supabase stack (see [`supabase/README.md`](../supabase/README.md)):

```sh
supabase start           # from the repo root
cd web
cp ../.env.example .env.local   # then fill in the publishable key from `supabase status`
pnpm install
pnpm dev                 # http://localhost:3000
```

Login emails don't go out locally: open Mailpit at http://127.0.0.1:54324 and click the link there.
Open it in the same browser you requested it from (PKCE flow; cross-device links are #46).

## Auth in short

- `src/proxy.ts` refreshes the session cookie on every request (Next.js 16 calls middleware "proxy").
- `src/lib/auth.ts` → `getUser()` / `requireUser()`: the only place pages check who's logged in. Components that call them must sit inside `<Suspense>` (Cache Components).
- `src/lib/supabase/{client,server,proxy}.ts`: one Supabase client per runtime.
- `/login` → magic link email → `/auth/callback` (exchanges the code for a session) → `?next=` page.

## Upload in short

`/upload`: the browser re-encodes the photo (`src/lib/prepare-photo.ts`: applies EXIF rotation, then drops all metadata, max 4000 px), uploads it straight to the private `insoles` bucket under the user's folder, then calls a server action that validates the form (`src/lib/submission-form.ts`) and creates the submission. The database enforces consent, folder, and at most 20 uploads per user per day. The browser step is for privacy, not security: the worker treats every file as untrusted (see #29).

## Check (same as CI)

```sh
pnpm lint                # ESLint
pnpm typecheck           # generates Next.js route types, then tsc --noEmit
pnpm test                # Vitest unit tests (tests/)
pnpm test:coverage       # ...with coverage → coverage/lcov.info
pnpm test:e2e            # Playwright: builds the app, starts it, runs e2e/ in Chromium
```

`test:e2e` needs `supabase start` running and `.env.local` filled in (including `SUPABASE_SECRET_KEY`): the login test reads its email from Mailpit, and the upload test downloads the stored photo to check that its metadata was removed. In CI this is the separate `e2e` job.

First-time Playwright setup downloads the browser: `pnpm exec playwright install chromium`.

`AGENTS.md` is generated by Next.js for AI coding assistants. It points them at the docs bundled in `node_modules/next/dist/docs/`, which match the installed version.

## Deploy (Vercel)

Vercel deploys the app through its GitHub integration; there is no deploy job in our CI.

| Trigger | Deploys to | Supabase project |
|---|---|---|
| Push to `main` | Production | `fitfinder-prod` (`usdetilhsblzfnezwdvs`) |
| Every PR | Its own preview URL (posted on the PR) | `fitfinder-staging` (`uhmeurzjiyvciifbpwzr`) |

- Vercel project root directory: `web/`
- `vercel.json` pins server functions to `dub1` (Dublin): next to the Supabase projects (`eu-west-1`, Ireland), and in the EU for GDPR
- Env vars are set in the Vercel dashboard per environment (Production / Preview): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- Each Supabase project's **Authentication → URL Configuration** must allow the matching Vercel URLs. Supabase only redirects magic links to URLs on this list; anything else falls back to the Site URL:

  | Project | Site URL | Redirect URLs |
  |---|---|---|
  | `fitfinder-prod` | `https://fitfinder-tau.vercel.app` | `https://fitfinder-tau.vercel.app/**` |
  | `fitfinder-staging` | `https://fitfinder-felixhaegeles-projects.vercel.app` | `https://fitfinder-*-felixhaegeles-projects.vercel.app/**` |

  The staging wildcard covers every preview URL (`fitfinder-<hash>-…` and `fitfinder-git-<branch>-…`). Previews are behind Vercel Authentication, so only the owner (logged in to Vercel) can open them
- Hosted Supabase projects get migrations via `supabase db push` (manual for now; automated in #34)
